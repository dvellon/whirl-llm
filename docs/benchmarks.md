# WHIRL release benchmark (v0.2.0) — WHIRL vs llama.cpp on the Radeon AI PRO R9700 and the Radeon 8060S

WHIRL 0.2.0 against the **official ggml-org llama.cpp release b11214**, its **ROCm** and its **Vulkan** Windows builds, each shown in its own column with its own lead. No other engine is compared on this page. Models: our two MXFP4 quantizations, **Swift-1.5 27B MXFP4** (dense) and **Ornith-1.5-35B-A3B MXFP4** (MoE). Every table below is generated by a script from the measured values (`release020/make_fullmx_tables.py` and `public_numbers.json` in the measurement workspace), with no hand-typed numbers.

**Read this first:**

- **WHIRL leads both llama.cpp builds in every measured cell**: both GPUs, both models, all three WHIRL modes, 2k to ~250k tokens, prefill and decode.
- **Three kinds of llama.cpp cells carry a footnote and are never used as a headline**: R9700 + Swift 27B at ~250k (llama.cpp's f16 KV does not fit in 32 GB and spills, ᵃ), R9700 + Swift 27B at 8k (llama.cpp's first long request was cold, ᵇ), and 8060S Vulkan prefill at 2k (Vulkan's short-prompt penalty on that GPU, ᶜ). One WHIRL cell is not measured: Swift 27B precise at ~250k on the R9700 (ᵈ, f16 KV does not fit).
- **Ornith decode is compared as shipped**: WHIRL with MTP drafts, llama.cpp without speculation, because its MTP was slower than plain decoding on this MoE model.
- **fast is not fully optimized yet** and is slower than balance on Ornith below about 64k tokens (§7).
- Every speculative-decoding number says what the reply was: **document QA** (part of the answer can copy code from the prompt) or **coding chat (new text)** (nothing to copy). Exact prompts in §2.1.

## 2. Methodology

- **Lengths**: 2k, 8k, 32k, 64k, 96k, 128k and ~250k tokens. "~250k" is the 256k prompt file, which is 249,510 tokens with this tokenizer; it is labelled ~250k everywhere.
- **Greedy decoding, thinking off, one user** (`-np 1`), tok/s from each server's own `timings`. One GPU job on the machine at a time (lock file), one server per engine, model and mode, a short warm-up request before each sweep.
- **Runs**: R9700, one request per cell. Radeon 8060S: WHIRL one request per cell; llama.cpp the median of 1 to 3 runs. Treat differences under about 5% as noise.
- **Coding chat**: WHIRL median of 3 runs on the R9700 and one run on the 8060S; llama.cpp first run only, because its n-gram drafts learn a repeated prompt (later runs copy the earlier answer).
- **llama.cpp decode mode**: Swift 27B = MTP + n-gram (`--spec-type draft-mtp,ngram-mod`), its fastest mode on the dense model; Ornith = plain decoding (as shipped), because its MTP was slower than plain on this MoE model. llama.cpp prefill comes from the same runs.
- **WHIRL**: `whirl-server MODEL --precise|--balance|--fast -np 1 --ctx-per-slot 262144 --kv-ssd-mode off`; MTP (+ n-gram) drafts on, as by default.

### <a id="prompts"></a>2.1 Exact prompts and how to reproduce

Speculative decoding is fastest when the reply is predictable (copying or reciting text), so here is exactly what each decode number replied to. Our own prompt files are in the repository under [`tools/bench/prompts/`](../tools/bench/README.md).

**Document QA** (the 2k to ~250k prefill and decode tables). The prompt is: a first line `【測試編號 <nonce>】` that is unique per request (so nothing hits a prefix cache), then a document built from permissively licensed real sources (C++, Python, Rust and TypeScript source files, Chinese technical documents, Chinese Wikipedia, English technical documents; each part headed `### 檔案 N：project/path（license）`, no repeated 4096-token windows), cut at a whole line to the target length, then `---` and this question, the same at every length ([`document_qa_question.txt`](../tools/bench/prompts/document_qa_question.txt), verbatim):

> 請根據上面第 1 個檔案（llama.cpp/src/models/muse-glimmer.cpp）中的函式 `graph`，用繁體中文說明它的用途、參數與回傳值，指出一個可能出錯的邊界情況，並寫出修改後能正確處理該情況的完整函式程式碼。

File 1 is at the start of every prompt, so the 256-token answer explains a function the prompt contains and rewrites it: part of it can copy code from the prompt, which helps the drafts of every engine that uses them (WHIRL MTP + n-gram, llama.cpp MTP + n-gram on Swift). The documents themselves are not redistributed, because they consist of third-party text under its own licenses.

**Coding chat (new text)** (512 tokens; one request after a 64-token warm-up), [`coding_chat_zh.txt`](../tools/bench/prompts/coding_chat_zh.txt), verbatim:

```text
請用 Python 寫一個命令列工具 `dedup.py`：掃描指定目錄（可遞迴）中的所有檔案，用檔案大小先分組、再用 SHA-256 找出內容完全相同的檔案，最後輸出每一組重複檔案的路徑與大小，並統計可以省下多少空間。要求：
1. 用 argparse，支援 `--min-size`（忽略太小的檔案）與 `--json`（改用 JSON 輸出）。
2. 大檔案要分塊讀取，不能一次讀進記憶體。
3. 遇到沒有權限或讀取失敗的檔案要略過並在最後列出。
4. 附上 pytest 測試，至少涵蓋：空目錄、兩個相同檔案、大小相同但內容不同。
請先簡短說明設計，再給完整程式碼。
```

The answer (explanation and code) is all newly written, and the prompt holds nothing to copy beyond a few option names: a hard case for speculative drafts.

**Coding-agent session** (§6): fixture [`agent_fixture.json`](../tools/bench/prompts/agent_fixture.json) and the exact turn protocol in [`tools/bench/README.md`](../tools/bench/README.md).

**Request and reproduction** (both servers, started as in §8; PowerShell):

```powershell
$prompt = Get-Content -Raw -Encoding UTF8 .\prompt.txt      # document QA prompt, or tools\bench\prompts\coding_chat_zh.txt
$body = @{ model = 'whirl'; messages = @(@{ role = 'user'; content = $prompt }); max_tokens = 256; temperature = 0;   # chat: 512
           chat_template_kwargs = @{ enable_thinking = $false } } | ConvertTo-Json -Depth 6
$r = Invoke-RestMethod http://127.0.0.1:8099/v1/chat/completions -Method Post `
       -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body))
$r.timings.prompt_per_second, $r.timings.predicted_per_second   # prefill tok/s, decode tok/s (same field names in both servers)
```

## <a id="agent-session"></a>6. Coding-agent session (R9700 and Radeon 8060S)

Swift 27B. Per session: a ~20k-token system + tools prompt (coding-agent instructions plus skills / MCP tool manuals) and a `read_file` tool returning a ~3.6k-token C++ source file, four user turns (explain the file, find the most complex function, rewrite it as code, review a resent edited copy), the full history resent on every call, one client, sequential, temperature 0, at most 384 tokens per call. WHIRL balance with its MTP + n-gram drafts; llama.cpp MTP + n-gram. Session 1 starts cold (the system + tools prompt is not cached yet) and reads `llama-batch.cpp`; session 2 shares that prefix and reads `llama-chat.cpp` (the same files for every engine). One round, a fresh server per engine.

## 7. Modes: what precise and fast cost or gain

<!-- gen:precise.en -->
precise costs speed. On the R9700 the biggest cost is prefill on MXFP4 files, which runs without fp8 in precise (Swift 27B at 2k: 1,702 vs 3,273 tok/s in balance; Ornith: 7,575 vs 11,550); in the coding chat Swift decodes 83.4 vs 109.6 tok/s. The 8060S has no fp8 matrix units, so there precise and balance prefill are close (479.1 vs 498.4, Swift at 2k). precise still leads both llama.cpp builds in every measured cell.
<!-- /gen -->

<!-- gen:fast.en -->
**fast mode is not fully optimized yet; it will improve in later 0.2.x point releases.** What it does today, measured: it mainly speeds up decode on the dense Swift 27B (R9700: 115.5 vs 87.6 tok/s in balance after a 2k-token document, 130.4 vs 109.6 in the coding chat; 8060S: 37.7 vs 32.5 at 8k) and long-context decode on the Ornith MoE (R9700 at ~250k: 125.3 vs 101.7). On Ornith it is **slower than balance below about 64k tokens** (R9700: 208.3 vs 238.4 at 2k, 183.5 vs 199.1 at 32k; at 64k 174.9 vs 169.1; 8060S at 2k: 93.8 vs 101.4), because its 4-bit KV cache adds a fixed cost per token that only pays off at long context. fast does not speed up prefill yet (2,790 vs 2,805 tok/s, Swift at 32k on the R9700).
<!-- /gen -->

Why precise at ~250k is missing on the R9700 for Swift 27B: precise keeps the KV cache in f16, and the f16 KV for 249,510 tokens does not fit next to the 27B weights in 32 GB; the f16 pool holds about 190k tokens. balance and fast use a smaller KV format there and run the full length. Ornith's KV cache is much smaller, so precise runs ~250k on both GPUs.
