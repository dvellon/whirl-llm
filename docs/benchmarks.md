# WHIRL release benchmark (v0.2.0) — WHIRL vs llama.cpp on the Radeon AI PRO R9700 and the Radeon 8060S

WHIRL 0.2.0 against the **official ggml-org llama.cpp release b11214**, its **ROCm** and its **Vulkan** Windows builds, each shown in its own column (never a best-of). No other engine is compared on this page. Every table below is generated by a script from the raw result files (`release020/make_public_tables.py` in the measurement workspace), so each cell traces to one measured row.

**Where WHIRL does not lead by much (read this first):**

- **Dense decode on the Radeon 8060S, document QA at 2k tokens**: +9% over llama.cpp ROCm and +6% over Vulkan at 2k tokens, within run-to-run noise. Dense decode there is memory-bound (about 256 GB/s for 15+ GB of weights); the lead grows with context (+24% to +48% from 32k on).
- **MoE decode is compared as shipped, not like for like**: WHIRL uses its MTP drafts; llama.cpp decodes the MoE model without speculation, because its MTP was slower than plain decoding on this model (R9700: slower in 11 of 12 cells, 0.4 tok/s faster in one).
- **precise costs speed**: on the R9700 it is 14–26% slower than balance in decode and 6–13% slower in prefill. **fast is not always faster than balance**: on the MoE model at short and medium context balance decodes faster.
- **Plain decoding without speculation** is memory-bandwidth bound in every engine; most of WHIRL's decode lead comes from MTP + n-gram speculative decoding.

## 2. Methodology

- **Prompts**: a long-document question-answering prompt at 2k, 8k, 32k, 64k, 96k and 128k tokens (8k on the R9700 only), each with a unique first line so no request hits a prefix cache; 256 generated tokens. Chinese-question coding chat: one Chinese coding question (Chinese explanation, English code), 512 tokens.
- **Greedy decoding, thinking off, one user** (`-np 1`), tok/s from each server's own `timings`. One GPU job on the machine at a time (lock file), one server per engine, model and mode.
- **R9700**: every cell measured in one run on 2026-10-16, one request per length (n = 1); WHIRL chat = median of 3; llama.cpp chat = first run only, because its n-gram drafts learn a repeated prompt (later runs reached 180–330 tok/s by copying).
- **Radeon 8060S**: at least 25 s of 2k-prompt warm-up before each sweep; engines interleaved, order rotated between rounds; cell = median of rounds (n = 1 to 3, marked); one cell (llama.cpp ROCm, dense, 96k decode) has two runs 31% apart and is marked unreliable.
- **llama.cpp decode mode**: dense = MTP + n-gram (on the R9700 plain decoding was measured too and MTP + n-gram was faster in every dense cell, so each cell shows the faster of the two, named per cell; on the 8060S only MTP + n-gram was run); MoE = plain decoding (as shipped). llama.cpp prefill on the R9700 = the faster of its two runs per backend; on the 8060S the prefill of the same runs as the decode.
- **WHIRL**: `whirl-server MODEL --balance|--precise|--fast -np 1 --ctx-per-slot 163840 --kv-ssd-mode off`; MTP (+ n-gram) on, as by default.

### <a id="prompts"></a>2.1 Exact prompts and how to reproduce

Speculative decoding is fastest when the reply is predictable (copying or reciting text). So here is exactly what each decode number replied to.

**Document QA** (the 2k–128k prefill and decode tables). The prompt is: a first line `【測試編號 <nonce>】` that is unique per request (so nothing hits a prefix cache), then a document built from permissively licensed real sources (C++, Python, Rust and TypeScript source files, Chinese technical documents, Chinese Wikipedia, English technical documents; each part headed `### 檔案 N：project/path（license）`, no repeated 4096-token windows), cut at a whole line to the target length, then `---` and this question, the same at every length (verbatim):

> 請根據上面第 1 個檔案（llama.cpp/src/models/muse-glimmer.cpp）中的函式 `graph`，用繁體中文說明它的用途、參數與回傳值，指出一個可能出錯的邊界情況，並寫出修改後能正確處理該情況的完整函式程式碼。

File 1 is at the start of every prompt, so the 256-token answer explains a function the prompt contains and rewrites it: part of it can copy code from the prompt, which helps the drafts of every engine that uses them (WHIRL MTP + n-gram, llama.cpp MTP + n-gram on the dense model).

**Chinese coding chat** (512 tokens; one request after a 64-token warm-up), verbatim:

```text
請用 Python 寫一個命令列工具 `dedup.py`：掃描指定目錄（可遞迴）中的所有檔案，用檔案大小先分組、再用 SHA-256 找出內容完全相同的檔案，最後輸出每一組重複檔案的路徑與大小，並統計可以省下多少空間。要求：
1. 用 argparse，支援 `--min-size`（忽略太小的檔案）與 `--json`（改用 JSON 輸出）。
2. 大檔案要分塊讀取，不能一次讀進記憶體。
3. 遇到沒有權限或讀取失敗的檔案要略過並在最後列出。
4. 附上 pytest 測試，至少涵蓋：空目錄、兩個相同檔案、大小相同但內容不同。
請先簡短說明設計，再給完整程式碼。
```

This is a hard case for speculative drafts: the Chinese question, the Chinese explanation and the English code are all newly written, and the prompt holds nothing for the reply to copy beyond a few option names (draft-based decoding is fastest when replies are predictable, such as copying or reciting known text; this row has none of that).

**Coding-agent session** (§5): a 16k-token skills / MCP system prompt, the `read_file` tool returning a 3.6k-token C++ source file from llama.cpp, then four user turns (explain the file; find its most complex function; rewrite that function as code; review an edited copy of the file sent in the message), each call resending the full history, at most 384 tokens per call.

[TBD: publish the prompt files (the document corpus with its per-file sources and licenses, the prompt builder, the agent-session fixture) in the repository or as a release asset, and link them here; owner decision, because the corpus contains third-party text under its own licenses.]

**Request and reproduction** (both servers, started as in §6; PowerShell):

```powershell
$prompt = Get-Content -Raw -Encoding UTF8 .\prompt.txt      # document QA prompt (or the chat prompt)
$body = @{ model = 'whirl'; messages = @(@{ role = 'user'; content = $prompt }); max_tokens = 256; temperature = 0;   # chat: 512
           chat_template_kwargs = @{ enable_thinking = $false } } | ConvertTo-Json -Depth 6
$r = Invoke-RestMethod http://127.0.0.1:8099/v1/chat/completions -Method Post `
       -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body))
$r.timings.prompt_per_second, $r.timings.predicted_per_second   # prefill tok/s, decode tok/s (same field names in both servers)
```

## 5. Coding-agent session (Radeon 8060S and R9700)

### 5.1 Radeon 8060S (max power as above)

Dense Qwen3.8-27B Q4_K_M. Per session: a 16k-token shared skills / MCP system prompt plus a `read_file` tool (a 3.6k-token source file), four user turns (explain the file, find the most complex function, rewrite it as code, review a resent edited file), full history resent on every call, one client, sequential, temperature 0, at most 384 tokens per call. ### 2. Methodology

#### 2.1 Rules

- **One measurement job at a time.** Each job checks that the R9700 reports status OK, takes the
  machine's R9700 lock, runs `whirl bench` or starts one server and waits for `/health`, measures, stops
  the server gracefully (Ctrl+C, so the KV tiers finish writing), releases the lock, checks the GPU status
  again and appends its rows to one results file.
- **Greedy decoding in both engines.** Requests send `temperature 0`; llama-server also runs with
  `--top-k 1`. Requests are the same bytes for both engines; llama-server runs with `--reasoning off`.
  The 7 coding prompts, the system-prompt and the restore tests send
  `chat_template_kwargs: {enable_thinking: false}`. WHIRL's server turns thinking on when a request
  does not say, so the decode-after-16k test (§6) and the 4-user test (§7) were re-measured with the same
  `enable_thinking: false` for every WHIRL version; the llama.cpp side already ran with `--reasoning off`.
- **Which run counts:** per case, model and executable only the **last** run counts (one job writes all
  its rows with one timestamp), except the 4-user server test (§7), which was repeated on purpose: its
  numbers are the **mean of all runs** (3 runs per version and model, llama.cpp 1).
  Rows a job marked as an error or warning are not used.
- **A fresh SSD tier per run:** every WHIRL server run gets its own `--kv-ssd-dir`, so no run restores a
  prompt of an earlier run (only the restore test reuses the directory, by design).
- **Same output:** WHIRL's greedy output is compared across versions by hash (`whirl bench`: its own
  hash; server: SHA-1 of the generated text, tool calls included without their random `id`). Every
  version comparison on this page produced the same output.
- **No measured run includes WHIRL's first-run GEMM autotune**; server timings start after start-up.
- **Ratio = WHIRL / llama.cpp**; "llama.cpp" is its **fastest** mode for that row (plain, MTP, MTP +
  n-gram), and the mode is named. For times (TTFT) the ratio is llama.cpp time / WHIRL time.
- "**no MTP**" marks plain decoding without any speculation. "N/A" = llama.cpp has no equivalent.

### 12. Exact commands

```bat
:: WHIRL CLI
whirl bench MODEL.gguf --prefill 8192 --decode 8 --modes plain
whirl bench MODEL.gguf --prefill 512 --decode 512 --prompt @zh_code.txt

:: WHIRL server (each run with its own SSD tier directory)
whirl serve MODEL.gguf --port 8099 --log-file LOG --kv-ssd-dir RUN\kvcache [-np 1 --ctx-per-slot 262144] [--kv-ram-mb 16384]
    (q8h KV: set WHIRL_KV=q8h; no MTP: set WHIRL_MTP=0 and WHIRL_NGRAM=0)

:: llama.cpp server

    --jinja --reasoning off --top-k 1 -np 1 -c 131072 [--cache-ram 16384]
    [--spec-type draft-mtp --spec-draft-n-max N --spec-draft-n-min 0 --spec-draft-p-min 0.3]
    [--spec-type draft-mtp,ngram-mod --spec-draft-n-max N --spec-draft-n-min 0 --spec-draft-p-min 0.3]
```
